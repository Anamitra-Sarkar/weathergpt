# WeatherGPT ML layer — real-world readiness report

**Audience**: whoever picks up `app/` integration next (see
`docs/MODEL_REGISTRY_INTEGRATION.md` for the how-to), and anyone assessing
whether these five models are usable in the live product.

**Date**: 2026-09-04. **Scope**: this document reports what was actually
measured, twice over — once on held-out data from the same generation
process as training (`test_heldout` in each model's `metrics.json`), and
once against live external APIs and genuinely never-templated input,
run through `modal_jobs/realworld_check.py`. The second pass exists because
held-out-but-same-distribution numbers can look good while still failing on
real phrasing, real edge-case weather, or real never-seen field names — this
report is the honest answer to "does it actually hold up outside its own
training data."

**Bottom line**: three of five models (M1, M2, M5) hold up well on live
data with no serious surprises. M4 has one cosmetic, immaterial defect.
**M3's intent output is not yet reliable on natural phrasing** — this is the
one finding in this report that should change how the next integration is
done, and the recommended fix (a much lower, explicitly-provisional
confidence threshold, rule parser as tie-breaker) is already reflected in
`docs/MODEL_REGISTRY_INTEGRATION.md`.

---

## Methodology

`modal_jobs/realworld_check.py` (committed, reproducible: `modal run
modal_jobs/realworld_check.py`) does five things, none of them reusing
cached or templated data:

1. Fetches **today's actual multi-model forecast** from
   `api.open-meteo.com/v1/forecast` at request time for 5 Indian locations
   spanning coastal, inland-plains, arid and hill-station climates — not
   curated to be easy, not all drawn from the training location set.
2. Runs that live forecast through **M2** (bias correction) and **M5**
   (source ranking).
3. Reuses the same live multi-model spread through **M4** (calibrated
   exceedance probability) — M4's trained interface is the 4-model summary
   statistics, the same shape M2 consumes.
4. Runs **M3** against 12 hand-written queries that were never generated by
   the D4 template/translation pipeline: casual phrasing, typos, "tmrw" /
   "rn" shorthand, code-switched Hindi and Tamil, and two deliberately
   out-of-domain questions to see how it fails.
5. Runs **M1** against 6 realistic field-name strings not in its D3 training
   tables (real ECMWF/GRIB short names: `2t`, `tp`, `10si`, `VIS`,
   `CAPE_180-0mb`, `PWAT_entire_atmosphere`).

There is no labelled gold answer for "was this the right intent for this
real sentence" — this is a smoke test read by a human, not an automated
gate. The full raw output is on the `weathergpt-data` volume at
`realworld_check_report.json`.

## M1 — field semantic mapper: **holds up**

| raw field | unit | mapped to | confidence |
|---|---|---|---|
| `2t` | K | `temperature_2m` | 1.00 |
| `tp` | m | `precipitation_amount` | 1.00 |
| `10si` | m s⁻¹ | `wind_speed` | 1.00 |
| `VIS` | m | `visibility` | 1.00 |
| `CAPE_180-0mb` | J kg⁻¹ | `cape` | 1.00 |
| `PWAT_entire_atmosphere` | kg m⁻² | **ABSTAIN** | 0.62 |

6/6 sound outcomes on strings it never saw during training: 5 correct
canonical mappings using real ECMWF/GRIB short names, and one honest
abstention rather than a fabricated guess on a genuinely obscure field
(precipitable water is a legitimate NWP field, just not one that appeared
in the D3 parameter tables). This is exactly the designed behavior — see
`docs/MODEL_REGISTRY_INTEGRATION.md` Site 1.

Held-out benchmark for context: `test_zeroshot_macro_f1 = 0.743` vs a 0.160
dict-lookup baseline, on schema families (`WRF`/`NCEP`) never trained on.

## M2 — distributional MOS (bias correction): **holds up, one edge case to guard**

Ran on 5 live locations × 3 variables. Corrections were numerically sane
and intervals bracketed the point value everywhere, **except one**:
Bikaner (an arid, low-wind location) had raw wind-speed forecasts of
`{gfs: 1.6, ecmwf: 5.4, icon: 4.4, gem: 6.5}` m/s (mean 4.5) and M2 corrected
this to **9.6 m/s**, with an 80% interval of `[5.8, 11.7]` — entirely above
every one of the four raw model values. That is a real, out-of-distribution
correction, not a bug in the code: low-wind desert conditions are
under-represented in the training corpus (D1/D2 skew toward monsoon-season,
higher-wind conditions), so the learned correction generalizes poorly to
this specific regime.

**Recommendation for the integration**: add a sanity bound in
`_apply_mos_correction` (Site 2 of the integration doc) — clamp or flag a
correction whose magnitude exceeds some multiple of the raw ensemble's own
spread, rather than emitting it to a user unguarded. This was not part of
the original integration sketch and should be added.

Held-out benchmark: positive CRPS skill vs. the raw ensemble on every
variable (temperature +4.7%, precipitation +13.2%, wind +8.9%), measured on
a spatially held-out set of locations.

## M3 — intent + slot parser: **slots usable, intent not yet reliable on natural phrasing**

This is the one model where live testing changed the picture from the
held-out numbers.

**Confidence collapses on real phrasing.** All 12 live queries returned
`intent_confidence` between **0.148 and 0.19** — for an 8-class classifier,
uniform guessing sits around 0.125, so the model is only marginally more
confident than "unsure" on anything that doesn't look like a D4 template.
A naive `confidence > 0.5` gate (an earlier draft of the integration doc
used exactly this) means **M3's intent would never fire on real user
input** — only on text phrased like its own training templates. Fixed in
`docs/MODEL_REGISTRY_INTEGRATION.md` to a lower, explicitly-provisional
0.35, with the rule-based parser kept as the deciding vote.

**Intent accuracy on natural phrasing is mixed even ignoring confidence:**

| query | predicted | assessment |
|---|---|---|
| "is it gonna rain today in puri or what" | `none` | reasonable (general query) |
| "should i take umbrella tmrw morning shillong" | `harvest` | **wrong** — plain rain query |
| "will there b flood risk near puri this wknd due to the cyclone" | `warning_check` | correct |
| "hey can u tell me if its safe for boats near puri tomorow morning" | `travel` | **should be `marine`** — near-identical template phrasing gets this right |
| "பயிருக்கு தண்ணீர் விட வேண்டுமா இன்று" (Tamil: should I irrigate today) | `irrigate` | correct |
| "mera cotton ka fasal kharab ho jayega kya is baarish se bikaner me" (will rain damage my cotton) | `irrigate` | **questionable** — this is a damage/warning question, not an irrigation request |
| "what's the capital of odisha" (out-of-domain) | `none` | safe — did not fabricate a weather intent, though it did extract "odisha" as a LOC span |

**Location and time slot extraction held up much better on the same
queries** — correct `LOC`/`TIME` substrings on 10 of 12, including through
typos and shorthand ("tmrw morning" → TIME span correctly isolated). This is
consistent with the held-out numbers (slot F1 0.988) and is the part of M3
safe to lean on today.

Held-out benchmark for context (see `backup/MODEL_RESULTS_LOG.md` for the
full retrain story, including a real bug found and fixed mid-session where
the variable head had silently collapsed to predicting nothing):
intent macro-F1 0.746 vs. 0.166 rule-parser baseline, slot F1 0.988,
variable macro-F1 0.120 (still weak — never use `variables` downstream).

## M4 — calibration: **holds up, one cosmetic defect**

Exceedance probabilities on live dry-weather forecasts (near-zero
precipitation forecast at all 5 locations) occasionally showed `P(>1mm)`
very slightly **higher** than `P(>0.1mm)` — e.g. Puri: `P(>0.1mm)=0.0`,
`P(>1mm)=0.0014`. This is backwards (a higher threshold must have equal or
lower exceedance probability) but the magnitude is negligible (≤0.003,
i.e. both are effectively "no rain") and does not change any real decision.
Root cause: each threshold's isotonic refinement is fit independently
(see `weathergpt_models/calibration.py`), so there's no cross-threshold
monotonicity constraint at the very low-probability floor. Worth a
follow-up (fit thresholds jointly, or clip to the previous threshold's
probability) but not urgent — flagging it here so it's a known quirk, not a
surprise.

Held-out benchmark: calibrated Brier score beats raw ensemble frequency at
every one of 6 thresholds; reliability curve is well-calibrated across the
full range (see `metrics.json`'s `reliability_test` — mean forecast vs.
observed frequency track within a few percentage points from 0.0 to 0.9).

## M5 — trust ranker: **holds up, face-valid**

Ranked ECMWF (`ecmwf_ifs025`) first for temperature at 4 of 5 live
locations — consistent with ECMWF IFS's well-known real-world edge in
global temperature skill, which is a reasonable face-validity check for a
model with no domain knowledge baked in, only learned skill. Wind-speed
rankings were more location-dependent (no single model dominated), which
matches the greater regime-sensitivity of wind forecasting generally.

Held-out benchmark: beats the fixed authority table on NDCG@1 for all 3
variables trained (temperature +9.3% RMSE skill, precipitation +6.0%,
wind +12.8%).

## What this means for shipping

| model | real-world verdict | safe to use as |
|---|---|---|
| M1 field mapper | ✅ solid | primary fallback when the dict lookup misses (Site 1) |
| M2 MOS correction | ✅ solid, needs a sanity bound | derived CEO alongside raw (Site 2) — add the bound described above first |
| M3 intent parser | ⚠️ slots yes, intent as a weak signal only | `LOC`/`TIME` slots: yes. Intent: tie-breaker behind the rule parser, not a source of truth |
| M3 variable head | ❌ not usable | do not call, at all (documented since the v1 retrain) |
| M4 calibration | ✅ solid | RADE's exceedance curve (Site 3) — this is still the highest-value integration point |
| M5 trust ranker | ✅ solid | ranking among the 4 trained NWP sources (Site 4) |

None of this changes the core integration guardrail already in
`docs/MODEL_REGISTRY_INTEGRATION.md`: every model output must degrade
gracefully to the existing deterministic path when the registry or a
specific model is unavailable, and every ML output must be emitted as a
provenance-bearing derived CEO, never presented as if it came directly from
a provider.

## Open items not covered by this report

- **Update 2026-09-04: published.** All 5 gate-passing models are now on
  the Hugging Face Hub at `Arko007/weathergpt-models` (private repo, 2.16 GB,
  model card auto-generated from each `metrics.json` — nothing typed by
  hand). `app/` can now load them with:
  ```python
  from weathergpt_models import ModelRegistry
  registry = ModelRegistry.from_hub("Arko007/weathergpt-models")
  ```
  This needs read access to the private repo (an HF token with read scope
  on that repo, passed the same way `huggingface_hub` normally authenticates
  — `HF_TOKEN` env var or `huggingface-cli login`). The remaining blocker is
  purely `app/`-side: no code under `app/` calls `ModelRegistry` yet — see
  `docs/MODEL_REGISTRY_INTEGRATION.md` for the exact integration points.
  Reproduce or re-publish with `modal run modal_jobs/export_models.py
  --repo-id Arko007/weathergpt-models --private` (uses the `arko007-hf-token`
  Modal secret; never pass a token on the command line or commit one to the
  repo).
- **No labelled real-world eval set exists yet.** This report is a smoke
  test, not a benchmark — there was no gold-labelled intent for the 12 live
  queries, so "wrong" above is a judgment call, not a scored metric. Once
  `app/` is live, logging real (anonymized) queries and periodically
  hand-labelling a sample would turn this into an actual tracked number
  and let the M3 confidence threshold above be tuned on real data instead
  of left as a placeholder.
- **`app/` integration itself has not been applied** — this report and
  `docs/MODEL_REGISTRY_INTEGRATION.md` are the specification; no code under
  `app/` has been changed to use `weathergpt_models` yet.
